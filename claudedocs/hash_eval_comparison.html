Hash 품질 — 전 세팅 종합 벤치마크

COCO test 5K · cross-modal 검색 · 학습한 모든 헤드 × Matryoshka 비트 전구간 × 12개 지표 (gold = 정답 기반, agreement@100 폐기). 생성: eval_all.py + eval_hashing.py

왜 이 문서? 이전엔 "개선됐다"만 적었는데, 여기서는 그동안 학습한 세팅 10개를 전부, 여러 gold 지표로 평가해 한 표에서 비교합니다. 핵심: 지표에 따라 결론이 갈립니다 — 정확한 쌍(pair-R@K)이냐 같은 개념(category-mAP)이냐.

1·A. 기본 용어
용어뜻
cross-modal서로 다른 모달(이미지↔텍스트) 간 검색. 같은 의미의 이미지와 텍스트를 가까운 코드로 만든다.
I2T / T2II2T=이미지를 쿼리로 텍스트를 검색 / T2I=텍스트를 쿼리로 이미지를 검색. 두 방향을 따로 측정.
query / gallery(corpus)찾는 쪽(query) / 검색 대상 풀(gallery=corpus). 여기서는 COCO test 5,000개.
pair (정답 쌍)같은 이미지에서 나온 이미지-캡션 1:1 짝(같은 cocoid). "정확히 그 짝"만 정답으로 보는 엄격 기준.
category relevanceCOCO 80개 물체 카테고리(사람·개·자동차…)를 1개라도 공유하면 "관련"으로 인정하는 느슨·등급(graded) 기준.
float embeddingSigLIP2가 뽑은 1152차원 실수 벡터. 양자화(비트화) 전 원본 → 성능의 천장(ceiling).
hash code (binary)float을 1비트(+1/−1)들로 압축한 코드. 저장·검색이 수십 배 싸고 빠름. 이 프로젝트의 산출물.
Matryoshka nested code한 번 학습으로 8·16·…·1024비트를 "앞에서 잘라" 모두 쓸 수 있게 만든 중첩 코드. 256비트 = 1024비트의 앞 256개.
prefixnested code에서 앞 K비트만 취한 것. 그래서 한 헤드가 여러 비트길이를 동시에 제공.
Hamming distance두 비트코드에서 다른 비트의 개수. XOR 후 1을 세면(popcount) 됨. 해시 검색의 거리 척도.
continuous vs binary (SignSTE)학습 땐 tanh(연속값), 추론 땐 sign(±1 이진). STE(straight-through)로 sign의 기울기를 흘려 학습 가능하게 함.
frozen backboneSigLIP2(backbone)는 고정(학습 안 함). 그 위의 작은 hash head만 학습 → 빠르고 broad 지식 보존.
RKD (관계형 distillation)float의 샘플 간 거리 구조를 hash가 따라하게 하는 손실. 절대 유사도가 아닌 상대 구조라 InfoNCE와 충돌 안 함.
CroVCA coding-rate코드가 한쪽으로 쏠리지 않게 다양성(coding rate)을 키우는 손실.
capped / uncapped(혼합비 통제) 추가 데이터(OI/CC12M)를 epoch당 고정량만 쓰면 capped, 전부 쓰면 uncapped. COCO 대비 학습 비중을 맞추려는 장치.
normalization (정규화)hash head 입력 float을 L2정규화하느냐(norm) 원본 그대로냐(raw). ablation으로 영향을 분리 측정.
1·B. 지표 상세 — 정의·범위·방향·한계 (3계열 + 진단)

방향: ↑=높을수록 좋음, ↓=낮을수록 좋음.

지표계열정의 / 수식범위·방향무엇을 보나 / 한계
R@1 / R@5 / R@10pair쿼리의 정답 쌍이 상위 K개 안에 있으면 1, 전 쿼리 평균.0–100% ↑정확한 짝을 얼마나 상위에 올리나. 한계: 정답이 1개라 가정 → "다르지만 유효"는 0점.
MRRpairmean(1 / 정답의 순위).0–100% ↑정답이 평균적으로 얼마나 위인가(상위 가중).
MedRpair정답 순위의 중앙값.1–N ↓쿼리 절반이 이 순위 안에 정답. 낮을수록 좋음.
mAP@100 / @1000category상위 K에서 Σ(정밀도@k · 관련@k) / (상위 K 내 관련 수).0–100% ↑"같은 카테고리"를 상위에 얼마나 모으나. 한계: relevance가 느슨(쿼리당 평균 32% 관련) → 절대값이 높게 나옴, 상대비교용.
NDCG@10categoryΣ(공유카테고리수 / log₂(순위+1)) ÷ 이상적 정렬값(IDCG).0–100% ↑더 많이 겹치는 항목을 더 위에 두는가(graded 보상).
P@10category상위 10개 중 관련(카테고리 공유) 비율.0–100% ↑첫 화면(10개)의 정밀도.
P@H≤2hash-nativeHamming 거리 ≤2로 검색된 것 중 관련 비율.0–100% ↑해시 버킷(반경2)의 순도. float은 측정 불가(반경 개념 없음).
R@H≤2hash-native반경2 안의 관련 수 ÷ 전체 관련 수.0–100% ↑버킷 룩업의 커버리지. 긴 코드일수록 0에 수렴(코드가 흩어져 반경2가 텅 빔).
cover@H2hash-native반경2 안에 1개라도 있는 쿼리 비율.0–100% ↑O(1) 버킷 룩업이 작동하는 쿼리 비율. 0%면 선형 스캔 강제.
bit_balance진단mean_k | (비트 k의 배치 평균) |.0–1 ↓(0=균형)각 비트가 +/− 50:50인가. 쏠리면 그 비트는 정보 0.
bit_indep진단‖ HᵀH/N − I ‖_F / K.↓(0=독립)비트끼리 독립인가. 상관 높으면 실효 코드길이↓.
entropy진단비트당 섀넌 엔트로피 H(p_k)의 평균.0–1 ↑(1=최대)비트당 실제 정보량.
quant_err진단mean(1 − |연속코드|).0–1 ↓(0=확실)sign으로 얼마나 확실히 ±1 갈렸나. 높으면 0 근처 애매비트 많음.
agreement@100 (폐기)—hash top100 ∩ float top100 / 100.—폐기. float=정답 아닌 proxy + 유효다양성 페널티 + top-100 경계노이즈 + distillation과 순환. gold로 재측정하니 데이터 효과를 거꾸로 봤음이 드러남.

1·D. 각 표·그래프 읽는 법
항목읽는 법
② 마스터표비트 버튼으로 코드 길이 선택, I2T/T2I 토글로 방향, 열 머리글 클릭으로 정렬. 초록=hash 중 그 열 최고, 파랑 행=float 천장, –=그 비트로 학습 안 된 세팅.
③ Matryoshka 곡선비트길이↑에 따른 R@10·mAP@1000 변화. 점선=float 천장. 색=세팅(아래 범례). 256 이후 평탄 = 한계효용.
④ hash-native 표비트별 P@H2 / R@H2 / cover. 초록 cover=룩업 잘 됨(≈100%), 빨강 cover=0%(반경2 안 텅 빔 → 버킷 룩업 불가).
⑤ 진단 표최장 비트 코드의 품질 4종(균형·독립·엔트로피·양자화오차). 초록=그 열 최고.

② ★ 마스터 비교표 — 비트길이 선택

비트 버튼/방향 토글 + 열 머리글 클릭=정렬. 초록=해당 열 최고(hash 중), 파랑행=float 천장. – = 그 세팅은 해당 비트로 학습 안 됨(256-max). float은 비트 무관(임베딩).

③ Matryoshka 비트길이 곡선

짧은 코드→긴 코드. 모든 세팅이 비슷한 곡선; 256 이후 한계효용 급감. demo만 512/1024 보유.

④ Hash-native — Hamming 반경 2 룩업 (I2T)

진짜 해시 버킷 룩업이 되는지. float은 이 지표 자체가 없음(반경 개념 없음).

핵심: 반경2 룩업은 ≥128bit에서 완전 붕괴(cover 0%). 32bit도 cover ~20%뿐. 즉 256bit 배포에선 O(1) 버킷 룩업 불가 → 선형 Hamming 스캔(faiss IndexBinaryFlat)이 필수. 짧은 코드(8bit)는 cover 100%지만 R@H2가 ~30%로 정밀도-재현율 trade.

⑤ 코드 품질 진단 — 256-bit (이미지 코드)

CC12M/데이터 확대는 bit_balance를 악화(COCO ~0.03 → CC12M ~0.12). balance 손실이 COCO엔 잘 듣지만 넓은 데이터에선 일부 비트가 치우침(entropy도 0.999→0.98). 즉 semantic mAP↑의 이면에 코드 균형↓ 비용이 있음.

⑥ 저장용량 비교 (비트길이별 · 분석적·정확)

벡터당 바이트 = 비트/8. float 기준 = SigLIP2 1152-d × 4B = 4,608 B. 비율 = float ÷ 코드. 코퍼스 크기별 총량도 표기.

해시의 핵심 이점 ①. 256-bit = 32B로 float 대비 144× 작음(1024-bit도 128B, 36×). 1억 벡터 코퍼스: float ≈ 461 GB vs 256-bit ≈ 3.2 GB. 메모리 상주·인덱스 비용을 좌우.

⑦ 검색속도 비교 (faiss 이진 vs float · 실측)

해시의 핵심 이점 ②. faiss IndexBinaryFlat(HW popcount)는 float 코사인 대비 수십 배 빠름. 비트가 길수록 Hamming 비용↑(이득↓)이지만 여전히 압도적. numpy popcount는 느려서 faiss가 실배포 경로. ⚠ 학습 중 측정이라 절대 ms는 ±, 상대 배율은 견고.

⑧ 혼합비 스윕 — in-domain sweet spot (COCO test, 1024-bit, I2T)

결합 974K 풀 고정, COCO:추가 데이터 step 비율만 변경. pair-R은 뒤집힌 U자(1:1~1:2 정점), category-mAP는 추가데이터만 있으면 포화.

⑨ 도메인-외 일반화 — Flickr30K · DOCCI (학습 안 한 벤치)

학습=COCO+CC12M+OI뿐. 미지 데이터셋 retrieval로 일반화 측정. 막대=R@1, 회색 점선=float 천장.

데이터(CC12M)가 도메인-외 일반화의 지배적 레버: baseline→CC12M I2T R@1 Flickr +8.7pt / DOCCI +18.1pt (도메인 차 클수록 이득↑). CC12M ≥ best-1:2 (두 벤치 모두) — in-domain best-1:2 우위와 대조. bit가 float R@10의 89%(DOCCI)~99%(Flickr) 유지.

⑩ 쿼리 robustness — 섭동(오타/단어드롭/truncation)

clean 쿼리 vs 섭동 쿼리. Stability@10=결과셋 안정성(↑robust), R@10 retention=정답 잔류율.

"비트가 더 견고" 가설 대체로 반증: bit1024가 결과셋 안정성(Stability)은 근소 우위지만, 정답 유지력(R@10 retention)은 float 우위. 무승부~float 약우위. 데모의 "반지의 제왕"은 양자화가 아닌 다국어 아티팩트.

⑫ 한국어 멀티링구얼 — 영어 vs 한국어 · fine-tune vs from-scratch

같은 5K COCO test 이미지, T2I, 1024-bit. 한국어 캡션 = coco_ko (test split, train 누수 없음). 학습 데이터에 한국어를 넣는 두 방식 비교 — B: from-scratch 혼합(COCO+KO 동시 학습), A: 기존 best 헤드를 한국어로 fine-tune.

① 한국어 이미 작동 — 학습에 한국어가 0개인데 KO R@10이 65%(best 헤드)에 달함. SigLIP2가 멀티링구얼이고 텍스트 헤드를 영·한이 공유하기 때문.
② fine-tune ≫ from-scratch — 같은 best 1:1 베이스에서 A'(ft113) KO 71.10 vs B(ml113) 65.92로 +5.18pt. from-scratch는 한국어가 풀의 10%로 희석되고, fine-tune은 한국어에 100% 집중하기 때문.
③ ft113 = 배포 후보 — KO 71.10 (float 66.06의 107.6% 추월) + EN 79.98 (영어 거의 손실 없음, in-domain −0.18pt) + Flickr/DOCCI OOD 회귀 미미 (⑨ 표 참조).
④ 교훈 — 소수 언어/도메인 강화는 from-scratch 혼합보다 fine-tune이 압도적으로 효율적이다.
